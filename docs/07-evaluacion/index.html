Permisos, datos expuestos, inyección y superficie de ataque. La API es el foco de riesgo.

CríticaS1.0✅ RESUELTO — dump.sql versionado expone hashes de contraseñas; admin y operativo compartían hash y la clave era "password"▶

El dump completo de la BD se commiteaba al repo con la tabla users y sus hashes bcrypt reales. Cualquiera con acceso al repo tenía las llaves; con "password" ni hacía falta crackear.

database/dump.sql

Resuelto 2026-07-13: 5/5 contraseñas rotadas a hashes únicos. Dump re-exportado con --ignore-table=gestion_wings.users — la tabla ya no viaja por git. Nuevo UserSeeder.php recrea cuentas sin contraseñas versionadas. Pendiente aparte (no incluido, requiere autorización): purgar el historial de git donde los hashes viejos ya quedaron.

CríticaS2.0✅ RESUELTO — API: alumnos, pagos, liquidaciones y clases sin control de rol▶

Todo eso estaba bajo auth:sanctum a secas. Un token de PROFESOR u OPERATIVO podía crear/borrar alumnos, liquidaciones y disparar pagos por la API — cosas que en la web están bajo ensure.admin. Escalada de privilegios.

routes/api.php:57,64-115 · AlumnoController.php (sin gate)

Resuelto 2026-07-13: se verificó primero que no hay ningún consumidor real (cero fetch/axios a /api/ en el front, sin config/cors.php) — auditar rol por ruta hubiera sido inventar permisos para un caso de uso inexistente. Se aplicó SS2.2: routes/api.php deshabilitada en bootstrap/app.php. Verificado: /api/* → 404, la web sigue en 200. Esto resuelve también S3, S4 y S6 de un saque.

AltaS3.0✅ RESUELTO vía API — Recibos PDF sin verificación de propiedad (IDOR)▶

El recibo de un pago se servía por pagoId sin comprobar derechos, vía API. Cualquier usuario autenticado podía iterar IDs y bajar los recibos de todos los alumnos.

routes/api.php:298-299

Resuelto 2026-07-13 junto con S2 (API deshabilitada). Pero: al investigar se encontró que el mismo problema existe en la ruta WEB equivalente, que sí tiene uso real — ver S9.0, nuevo, sin resolver.

AltaS4.0✅ RESUELTO — API login sin throttle (fuerza bruta)▶

El login de la API no limitaba intentos (la web sí). Combinado con claves débiles conocidas (S1), era la vía práctica de entrada.

routes/api.php:34

Resuelto 2026-07-13: la ruta /api/auth/login dejó de existir junto con toda la API (fix S2).

AltaS9.0✅ RESUELTO — Recibo de cuota por WEB sin control de rol ni de propiedad (IDOR real)▶

Encontrado al verificar el impacto de apagar la API para S2: la ruta web.recibos.cuota (la que de verdad usa caja/detalle para el botón de recibo) estaba solo bajo auth, sin gate de rol. Un PROFESOR logueado podía pedir /recibos/cuota/1, /2… y bajar el recibo de cualquier alumno.

routes/web.php:224 · ReciboController.php · Pago.php

En cuota() se bloquea solo al PROFESOR → 403. Probado: admin 200, operativo que cobró 200, operativo que NO cobró 200, profesor 403. Modelo de permisos documentado en docs/02-contratos/PERMISOS-ROLES.md (el operativo NO ve "solo lo suyo" — error que se repetía).

🗄️ Arquitectura de datos

Base bien construida (dinero en decimal, FKs, índices). El problema serio es un UNIQUE mal diseñado.

CríticaD1.0El UNIQUE de alumno_planes rompe el 2º cambio de plan (bomba latente)▶

activo es NOT NULL y hay UNIQUE(alumno_id, activo). Al cerrar planes con activo=0, un alumno puede cambiar de plan una sola vez: el segundo cambio da violación de constraint → error 500. Hoy no estalló porque nadie cambió dos veces.

migration create_alumno_planes:24 · AlumnoPlan.php:33-40

  • SD1.1 ⭐Hacer activo nullable y guardar NULL (no 0) en los cerrados; MySQL permite múltiples NULL, el UNIQUE sigue garantizando un solo activo. Migrar los 0 a NULL.
  • SD1.2Quitar el UNIQUE de la BD y enforcar en aplicación (el boot ya lo hace).
  • SD1.3Índice único parcial emulado con columna generada (más complejo).
AltaD2.0referencia_tipo es string libre con valores inconsistentes para lo mismo▶

El servicio marca el reflejo de caja como CAJA_OPERATIVA pero el seeder usó MOVIMIENTO_OPERATIVO para lo mismo. Ya causó el bug de movimientos duplicados en el historial.

cashflow_movimientos.referencia_tipo

  • SD2.1 ⭐Constantes/enum en el modelo y usarlas en todos lados; normalizar los datos existentes.
  • SD2.2Al menos documentar el conjunto válido y corregir el seeder.
AltaD3.0Liquidación acopla profesor↔subrubro por nombre exacto▶

El pago de liquidación busca un subrubro cuyo nombre es "Deporte-Nombre Apellido". Si el nombre cambia o el subrubro no existe, falla con error genérico sin aviso.

LiquidacionPagoService · LiquidacionWebController:276

  • SD3.1 ⭐Agregar subrubro_id (FK) al profesor y usar la relación en vez del nombre.
  • SD3.2Mínimo: verificar existencia antes de mostrar el formulario y avisar.
MediaD4.0Columna muerta pagos.forma_pago_id (con su FK y tabla)▶

La forma de pago se quitó del flujo pero quedó la columna, su FK y la tabla formas_pago sin uso.

pagos.forma_pago_id · tabla formas_pago

  • SD4.1 ⭐Si no vuelve, migración que elimine la columna, la FK y la tabla (y su pantalla de config).
  • SD4.2Dejar la columna pero sacarla de fillable y de las vistas.
MediaD5.0Índice redundante en deuda_cuotas▶

Coexisten index(alumno_id,periodo) y unique(alumno_id,periodo) sobre las mismas columnas. El UNIQUE ya indexa; el otro es redundante.

migration create_deuda_cuotas:27,30

MediaD6.0Estados de negocio como strings libres, sin dominio cerrado▶

Los estados (deuda, caja, pago, liquidación, revisión) viven solo como constantes PHP; la BD acepta cualquier string. Un typo mete un estado inválido que nadie detecta.

AltaI4.0El seeder no representa la operación real (causa de bugs invisibles)▶

Solo cobra cuotas en efectivo, un operativo, sin egresos ni cancelaciones ni rechazos. Con datos así los totales parecen correctos aunque la lógica esté mal — por eso los bugs de dinero fueron invisibles.

DemoSeeder.php

  • SI4.1 ⭐Rehacer con datos que ejerciten todos los flujos (egresos, varios medios, 2 operativos, cancelaciones, rechazos, deudores, inactivos, cambios de plan).
  • SI4.2Mantener el actual + un segundo seeder "estrés" con casos borde.
